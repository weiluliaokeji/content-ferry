# ContentFerry 产品交互重设计

> 日期：2026-07-19
> 目标：从“功能验证页面”重构为面向自媒体作者的日常工作台

## 1. 重设计原则

1. 用户围绕文章和运营任务工作，不围绕系统内部的“简报、审核门、数据库状态”工作。
2. 首页只回答三件事：今天优先做什么、哪些任务卡住、最近发布效果如何。
3. 文章创作使用独立全屏工作台，不在弹框中完成长内容编辑。
4. AI 出现在用户需要帮助的位置：选题、补充资料、提纲、段落修改、标题、摘要、配图、质量优化，不让用户手工搬运内容。
5. 自动化是默认路径；登录、验证码、网页变化或结果不确定时才请求人工接管。
6. 扫描文章库不是终点。扫描成功的文章必须进入工作台（未归档集合），可打开、编辑、预览、生成渠道稿和发布。
7. Markdown 是存储格式，不是强迫普通用户使用的编辑方式。

## 2. 一级导航

采用竞品常见且易理解的“左侧固定导航 + 右侧工作区”。当前已实现的一级导航如下（2026-08-26 与实现及 §4.1 职责边界对齐）：

| 导航 | 主要内容 |
| --- | --- |
| 工作台 | 今日任务、继续创作、待处理异常、最近发布数据；新建 / 修改 / 发布未发布稿；扫描导入 VitePress 外部文章 |
| 归档库 | 已归档文章查阅：检索、按渠道看发布状态、读正文、查看发布记录；轻量"重新发布"出口 |
| 发布记录 | 两段式：上段「待处理」列尚未确认最终结果的任务（微信草稿/待预览/待发布、各渠道进行中任务、以及系统判定失败但未经人工核实的任务）；下段「发布记录」列已确认终态任务（已发布、已取消，以及用户在平台后台核实后人工标记为失败的记录，后者显示红色「已失败」徽标与核实依据） |
| 技能与模型 | AI 服务、技能、浏览器会话 |
| 账号 | 多平台多账号、账号定位、凭据与连接健康 |
| 运行日志 | 运行日志、排查与排障 |
| 使用帮助 | 首次上手、配置缺口、主路径与常见故障 |

说明：

- “创作”不单列为导航，新建文章入口内置于工作台（见 §3）；“发布”入口归属工作台，发布状态集中在“发布记录”（见 §4.1）。
- 素材库、数据、设置为规划中能力，不在当前左侧导航；一期未完成的导航可以显示“即将开放”，但不能把所有未完成能力堆在首页。

## 3. 工作台

创作方向已整理但尚未生成提纲的项目，同时提供“编辑创作方向”和“生成提纲”。前者打开可编辑的简报以补充创作主题或想法、写作目标、目标读者、核心角度和已有资料；后者直接调用模型。两项操作并列，用户可按当下需要选择，不把编辑设为生成的强制前置步骤。生成提纲或正文时，界面必须在编辑区域逐步写入已收到的内容；尚未收到首段内容时，以可见的加载状态展示当前阶段和已等待时间，不能只留下静态提示语。宽弹窗须受当前视口宽度约束，长标题或编辑器内容不能触发页面级横向滚动。

点击“新建文章”后，用户在同一表单中填写主题/想法，并可选填发布账号、写作目标、目标读者、核心角度、已有资料和标题；主题是唯一必填项。提交时统一创建文章与简报并直接进入联网补研，不再打开第二个“确认创作方向”窗口。已创建项目仍可通过“编辑创作方向”修改全部字段；该编辑窗口在末尾保留可编辑标题和“让阿文推荐标题”，让推荐拥有完整上下文，推荐结果在原位供选择，历史系列仅作为可见参考。

“第三步：补充资料”除资料卡筛选外，还应提供紧邻资料卡的“继续补研”输入区。用户可以自然语言补充要核查的事实、优先来源、时间范围、反例或排除项；点击后在原窗口保留已有结论和资料卡，以按钮的进行中状态展示阿文正在补研。新结论追加到研究结论中，重复 URL 不新增资料卡；该轮用户要求和阿文回应会作为本文最早的阿文会话记录，供进入编辑器后回看。

新建文章时，如当前仅有一个已绑定账号，自动选中它作为发布账号；有多个账号时保留“暂不选择”，由用户明确选择，避免把内容误投到错误平台。

新建校验失败必须指出具体字段和原因（例如主题过长、标题为空或账号格式错误），不能只显示笼统的“提交信息不符合要求”。

“技能与模型 → 联网检索服务”中的 Tavily 连接测试必须在当前弹窗内立即给出可见结果：成功时展示已获得的测试结果数量，以及未保存 Key 还需保存的下一步；失败时展示服务返回的具体原因。不得仅结束加载状态而没有反馈。

首页默认结构：

1. 顶部显示当前工作空间、AI 连接状态、公众号连接状态。
2. 主操作为“新建文章”。
3. “继续创作”显示最近 3 个未完成项目，并给出业务化下一步。
4. “需要处理”只显示真实异常，例如朱雀需要接管、微信回调失败、IP 白名单变化、定时任务错过。
5. “最近发布”显示最近文章和基础数据。

不在首页直接展示账号添加表单、文章库路径输入框或长列表配置。

## 4. 归档库

归档库的已归档文章仍以 VitePress `docs/posts/<标题>/index.md` 为正文事实源。ContentFerry 创建的项目会在点击"新建文章"时立即生成该文件；扫描出的已有文章直接进入同一个编辑和发布流程。项目数据库只补充 AI 简报、提纲、检测和发布状态，不另存一份用户需要维护的正文。

每行显示标题、来源、账号、更新时间、状态和下一步操作。支持搜索和筛选。已有文章至少支持：

- 打开并编辑正文；
- 保留原 Front Matter，只编辑正文和明确开放的元数据字段；
- 查看网站发布字段 `publish` 与 `tags`；
- 发起公众号渠道稿生成；
- 查看历史发布记录；
- 外部文件变化时提示冲突，不静默覆盖。

账号、作者、摘要和封面统一在创作工作台右侧“发布设置”维护。点击“准备发布”只执行缺项检查和确认，不再出现第二套可编辑表单。

**发布设置按账号平台切换（2026-09-05 确认）：** “发布账号”决定发布去向，切换账号后配置项随之切换，平台专属参数不在这里维护第二份：

- 选**微信公众号**：显示微信留言、申请原创声明、开启赞赏、加入合集等微信专属选项，顶栏按钮为“准备发布”；
- 选 **CSDN / 博客园 / 掘金 / 51CTO**：面板内提示“在 XX 渠道稿中发布”，顶栏按钮变为“进入 XX 渠道稿”，点击后先保存文章设置再打开对应渠道稿；这些平台的栏目、分类、标签、发布形式等平台专属设置全部在渠道稿中填写，这里保存的作者、摘要和封面会带到渠道稿。

此前非微信平台选了账号后既没有对应配置项，顶栏“准备发布”又只会打开微信专用的同步草稿弹窗（提示“不是微信公众号”），形成死路。归档库“重新发布”入口正是走这条路径，因此必须按平台交接。

归档库的归档与查阅定位、与工作台的职责边界及发布入口归属见 §4.1。

## 4.1 工作台与归档库的职责边界（2026-08-26 确认）

两模块按"活跃工作集 vs 归档仓库"划分，明确"哪里操作、哪里查阅"，降低认知负荷。划分依据是 VitePress 源文件 Front Matter 中的 `archived` 布尔标记（随正文一起持久化，重新扫描不会丢失，无需数据库迁移）。

**工作台 = 未归档集合视图。** 基于 VitePress 目录扫描结果，不含 `archived: true` 的文章。范围包括：

- 本应用通过"新建文章"创建的草稿；
- 外部直接写入 VitePress 目录、经扫描纳入的文章；
- 任何尚未标记为归档的文章（含从未发布、部分渠道已发布、正在重发的文章）。

工作台提供完整操作：新建、修改、发布到各平台（微信公众号 / CSDN / 博客园 / 掘金）。

**归档库 = 已归档集合视图。** 只展示 `archived: true` 的文章，以查阅为主：检索历史文章、按渠道查看发布状态、阅读正文、查看发布记录；每行右侧提供 ⋯ 图标展开操作区，收拢"重新发布"与创作档案查阅入口，不实现第二套发布 UI。

工作台与归档库共用同一套渠道状态条：固定展示每个已接入平台的品牌图标和状态图标，尚未生成渠道稿时明确显示“未”，工作台额外显示有边框的创建/继续按钮；归档库只负责状态查阅。首次进入应用时，四个平台的渠道稿与发布任务必须与文章库并行加载，状态条不得先以空数据渲染、再依赖切换页面才校正。两处列表的文章标题后均显示浅灰小字号的完整创作时间戳。发布记录的最终状态固定在列表右侧，不能因长标题换行或下移；完成记录的元信息不重复显示最终状态。

**归档判定（已落地）：**

- `archived` 标记为 true 的文章进入归档库；为 false（或字段缺失）的文章留在工作台；
- 自动归档：当某文章所有已接入账号的渠道（只看实际配置了账号的平台）均达到 `published` 终态时，自动将 `archived` 设为 true；
- 存量迁移：应用首次启动时自动把 2026-08-11 之前创建且尚未归档的文章一次性标记为 `archived`（用于把存量历史文章迁移进归档库），并通过 `appSettings.legacyArchiveMigrationDone` 保证只执行一次；
- 工作台列表按文章创建时间倒序排列（与归档库排序一致）；工作台为空但存在已归档文章时，提示去归档库查看。

**文章生命周期与发布入口归属（方案 A）：**

- 首次发布在 **工作台** 发起；
- 已归档文章如需换渠道或重发，从归档库 ⋯ 展开操作区的"重新发布"轻量入口跳回工作台，复用同一套发布流程；发布逻辑只维护在工作台；
- 状态机：未归档（工作台）→ 全平台发布 → 自动归档（归档库）；后续重发由归档库轻量出口回到工作台，两条路径闭环。

## 4.2 归档库操作区与创作档案查阅（2026-08-29 确认）

归档后文章的操作入口与创作过程资产查阅方式：

- **收拢为图标展开区**：每行右侧只保留一个 ⋯ 图标按钮，点击后在该行下方展开操作面板；展开态独占，展开一行会自动收起上一行。行内默认保持安静，也避免为没有创作记录的文章渲染无意义按钮。
- **操作按文章实际记录出现**："重新发布"恒有；"查看创作方向""查看素材""查看提纲"仅当该文章存在文渡内容项目（按 `source_relative_path` 反查）且对应资产已就绪时出现。外部直写文章没有内容项目，展开后只显示"重新发布"并给出说明。
- **按需懒加载**：创作档案在首次展开时才按文章相对路径反查项目及其就绪标志，不在列表渲染时逐行请求。
- **工作台同步**：生成提纲或正文后，"编辑创作方向"改为"查看创作方向"。此前该入口在成文后被隐藏，导致创作简报与用户原始资料笔记无法再回看。
- **只读语义**：从归档库打开的提纲沿用已发布文章的只读模式，不形成第二份可编辑正文。

**外部直写文章的纳入：**

- 文章可绕开工作台、直接手写进 VitePress 目录，其创建不发生在工作台；
- 工作台须提供“扫描 VitePress 目录 / 导入外部文章”动作（复用现有“重新扫描文章库”能力），将未索引的外部文章纳入并显示、可编辑、可发布，与工作台原生稿能力一致；
- 不强制用户先“认领”外部文章，发现即可编辑 / 发布；
- 无论来源，点文章均用同一编辑器直接改 VitePress 源文件，编辑能力无“原生 / 外部”差别。

## 5. 全屏创作工作台

### 5.1 页面布局

全屏工作台不使用模态弹框：

```text
┌ 返回归档库 | 标题 | 保存状态 | 预览 | 发布准备 ┐
├────────┬────────────────────┬───────────────┤
│文章导航 │   所见即所得正文编辑区 │ AI 助手/手机预览 │
│资料来源 │                     │ 文章设置/质量优化 │
│素材库   │                     │               │
└────────┴────────────────────┴───────────────┘
```

- 左栏可以折叠，显示文章大纲、资料和素材。
- 中间是唯一主滚动区，页面外壳不跟随长文章滚动。
- 右栏可在“AI 助手、手机预览、文章设置、质量优化”之间切换。
- 顶部保存栏固定，显示“正在保存 / 已保存 / 保存失败”。
- 当目标账号是微信公众号时，文章设置还包含“申请原创声明”“开启赞赏”和“加入合集”。从工作台的微信公众号“设置并发布”进入编辑器时，若文章尚未保存发布账号，自动选中第一个已绑定的微信公众号账号；已有选择不覆盖。新建文章时“作者”默认填为最近使用过的作者，“申请原创声明”与“开启赞赏”默认已勾选，用户可按需取消。设置旁明确说明：创建草稿后会由可见浏览器尝试填写；用户仍需在微信后台核对并点击最终发布。发布记录的主操作为“在微信后台完善并发布”，而不是让用户回忆草稿箱位置。

### 5.2 编辑能力

基础能力至少与公众号图文写作相匹配：

- 标题、作者、摘要、封面；
- 标题层级、粗体、斜体、删除线、引用、列表、分割线、链接；
- 图片选择、拖拽、粘贴、替换、裁剪、压缩、alt 文本和图注；
- 表格、代码块和一键清除格式；
- 撤销/重做、字数、图片数、预计阅读时长；
- 手机端实时预览；
- 公众号排版主题；
- Markdown/Word 导入和 Markdown 源码切换作为高级能力。

编辑器技术路线优先评估 `doocs/md` 的公众号主题与渲染能力，并比较 Tiptap 的图片上传、拖拽、可扩展节点和 React 集成。现有 Milkdown 只作为过渡实现，不再继续围绕其堆叠公众号专用能力。

### 5.3 图片生命周期

1. 用户选择、拖拽或粘贴图片；
2. 图片先保存到当前文章的本地素材目录；
3. 自动生成预览图并提供压缩、裁剪；
4. Markdown 保存稳定的 ContentFerry 素材引用，不保存临时 `blob:` 地址；
5. 发布微信公众号前上传到目标账号素材库，并在冻结的渠道渲染包中替换为微信 URL；
6. 同一图片按文件哈希和目标账号复用远端素材。

## 6. AI 辅助方式

AI 助手不是单独的“生成全文”按钮集合，而是与当前选择和文章状态相关：

- 未选文字：继续写、调整全文结构、生成标题/摘要、检查账号定位；
- 选择文字：改写、扩写、缩写、举例、降低套路感、调整语气；动作选择后提供“补充要求（可选）”输入框，用于说明语气、目标读者、保留项、避免项或具体目标，支持 `Ctrl+Enter` 直接生成建议。
- AIGC 特征检测未选中文字时默认检测当前正文全文，按钮明确显示“检测全文内容”；选择文字后仅检测选区，按钮改为“检测选中内容”。正文为空时禁用检测，避免把空请求发送到外部检测工具。
- 资料面板：搜索补充资料、生成资料卡、插入引用候选；
- 图片面板：生成配图建议、AI 生成图片、裁剪和封面建议；
- 所有 AI 结果先预览差异，再由用户应用，不直接覆盖正文。选区快捷操作是向阿文补充“选区、动作与可选要求”的快捷入口；其请求和结果必须保存到本文阿文会话，并在会话内提供接受/拒绝建议的操作，不能因重新选择正文而丢失。
- 阿文的可应用建议必须锚定到唯一的正文片段；用户“同意”或“拒绝”后立即持久化处理状态。正文只显示待处理且仍可锚定的建议；阿文会话必须保留原建议、替换文本与“已接受”“已拒绝”或“无法定位”的最终记录，不能为清理正文浮窗而删除会话历史。
- 编辑模式切换使用紧凑图标按钮并提供悬停说明；视觉模式切换器靠工具栏右侧对齐，Markdown 模式沿用同一编辑器工具栏的背景、边框和层次，不能因模式切换出现突兀的配色变化。
- 建议卡默认显示在对应段落之后并为其预留空间，不遮盖后续正文；用户可拖动卡片，拖动偏移相对该段落保存，切换所见即所得与 Markdown 原文后仍回到同一锚点。
- 多条建议命中同一段落时，建议卡按生成顺序垂直堆叠并分别保留操作入口，不能相互遮盖而只显示最后一条。
- 阿文请求发出后，用户消息必须先显示“正在发送”；模型或网络失败时保留原消息并在消息旁说明失败，不能静默移除用户已经发送的内容。
- 失败消息提供就地“重新发送”操作；重试复用同一客户端消息 ID，避免因网络中断而在会话中重复保存同一条用户输入。
- 对旧版本留下的历史会话，若最后一条为用户消息且其后没有阿文回复，也应标为未完成并提供同样的重发入口。

## 7. 朱雀自动检测技能

主路径：

1. 用户点击“自动检测 AI 特征”；
2. ContentFerry 保存当前正文快照和哈希；
3. 打开持久化的可见浏览器会话；
4. 自动进入腾讯朱雀文本检测页；
5. 自动填入正文并触发检测；
6. 等待结果稳定，读取总体指标和可识别的疑似片段；
7. 保存结果、截图、检测时间和执行方式；
8. 返回编辑器右栏，按疑似片段提供定位和 AI 优化建议。

仅在以下情况进入人工接管：

- 尚未登录；
- 出现验证码或安全验证；
- 页面结构变化，无法可靠定位输入或结果；
- 内容长度超出网页限制；
- 结果读取不确定。

接管时保持浏览器可见，并在 ContentFerry 中显示“等待你完成登录/验证”。用户完成后点击“我已处理，继续自动检测”，技能从检查点恢复。人工回填放在折叠的“无法自动读取结果”兜底区，不作为默认操作。

## 8. 竞品启示与 ContentFerry 差异

新榜小豆芽与蚁小二的共同优势是左侧模块导航、多账号集中管理、内容发布和素材集中管理；公众号编辑工具的共同模式是中间编辑、图片/素材入口、手机预览及发布设置。

ContentFerry 不照搬它们的“批量分发工具”定位，而形成以下差异：

- 从主题、想法和资料开始的 AI 研究与创作；
- VitePress/Obsidian 文章库双向使用；
- 微信公众号官方 API 发布闭环；
- 朱雀自动检测与可恢复人工接管；
- CSDN 独立渠道稿与受控自动发布；
- 主稿、渠道稿、检测与发布回执的可恢复工作流。

## 9. 实施顺序

1. 应用外壳、工作台和一级导航；
2. 统一文章库视图（工作台 + 归档库），支持打开 VitePress 已有文章；
3. 全屏创作工作台和稳定保存；
4. 图片插入、本地素材和手机预览；
5. AI 选区助手；
6. 朱雀自动检测技能；
7. 微信渲染包、预览和发布设置；
8. 发布日历与数据回收。

## 10. 帮助与上手

- 左侧“帮助”提供短而可执行的首次上手入口，只展示当前配置缺口、四步主路径和常见故障，不复制整份需求文档。
- 完整说明使用仓库中的`docs/USER-GUIDE.md`作为可版本管理的主文件，安装包携带该文件；应用内提供“打开完整说明”入口。
- 完整说明覆盖数据目录、模型连接、VitePress 文章库、微信公众号 AppID/AppSecret、IP 白名单、回调、创作、检测、发布、日志和备份。

- Markdown 是说明书的唯一维护源，后续可从同一内容生成网站 HTML 和 PDF；不使用难以审查差异的 MHTML 作为源文件。
