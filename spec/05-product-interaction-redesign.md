# ContentFerry 产品交互重设计

> 日期：2026-07-19
> 目标：从“功能验证页面”重构为面向自媒体作者的日常工作台

## 1. 重设计原则

1. 用户围绕文章和运营任务工作，不围绕系统内部的“简报、审核门、数据库状态”工作。
2. 首页只回答三件事：今天优先做什么、哪些任务卡住、最近发布效果如何。
3. 文章创作使用独立全屏工作台，不在弹框中完成长内容编辑。
4. AI 出现在用户需要帮助的位置：选题、补充资料、提纲、段落修改、标题、摘要、配图、质量优化，不让用户手工搬运内容。
5. 自动化是默认路径；登录、验证码、网页变化或结果不确定时才请求人工接管。
6. 扫描文章库不是终点。扫描成功的文章必须进入工作台（未归档集合），可打开、编辑、预览、生成渠道稿和发布。
7. Markdown 是存储格式，不是强迫普通用户使用的编辑方式。

## 2. 一级导航

采用竞品常见且易理解的“左侧固定导航 + 右侧工作区”。当前已实现的一级导航如下（2026-08-26 与实现及 §4.1 职责边界对齐）：

| 导航 | 主要内容 |
| --- | --- |
| 工作台 | 今日任务、继续创作、待处理异常、最近发布数据；新建 / 修改 / 发布未发布稿；扫描导入 VitePress 外部文章 |
| 归档库 | 已归档文章查阅：检索、按渠道看发布状态、读正文、查看发布记录；轻量"重新发布"出口 |
| 发布记录 | 两段式：上段「待处理」列尚未确认最终结果的任务（微信草稿/待预览/待发布、各渠道进行中任务、以及系统判定失败但未经人工核实的任务）；下段「发布记录」列已确认终态任务（已发布、已取消，以及用户在平台后台核实后人工标记为失败的记录，后者显示红色「已失败」徽标与核实依据） |
| 技能与模型 | AI 服务、技能、浏览器会话 |
| 账号 | 多平台多账号、账号定位、凭据与连接健康 |
| 运行日志 | 运行日志、排查与排障 |
| 使用帮助 | 首次上手、配置缺口、主路径与常见故障 |

说明：

- “创作”不单列为导航，新建文章入口内置于工作台（见 §3）；“发布”入口归属工作台，发布状态集中在“发布记录”（见 §4.1）。
- 素材库、数据、设置为规划中能力，不在当前左侧导航；一期未完成的导航可以显示“即将开放”，但不能把所有未完成能力堆在首页。

## 3. 工作台

提纲编辑提供“暂存提纲”动作，暂存版本独立于正式提纲，不使项目进入 `outlineReady`；重新打开时优先恢复暂存版本。明确的“确认提纲并标记为已就绪”动作才会写入正式提纲并推进项目状态；“放弃本次修改”关闭编辑器且不保存本次修改。

创作方向已整理但尚未生成提纲的项目，同时提供“编辑创作方向”和“生成提纲”。前者打开可编辑的简报以补充创作主题或想法、写作目标、目标读者、核心角度和已有资料；后者直接调用模型。两项操作并列，用户可按当下需要选择，不把编辑设为生成的强制前置步骤。生成提纲或正文时，界面必须在编辑区域逐步写入已收到的内容；尚未收到首段内容时，以可见的加载状态展示当前阶段和已等待时间，不能只留下静态提示语。宽弹窗须受当前视口宽度约束，长标题或编辑器内容不能触发页面级横向滚动。提纲审核页在编辑器下方提供轻量的“和阿文一起优化”面板，分为“优化提纲结构”和“优化文章标题”：结构模式展示完整 Markdown 建议预览；标题模式展示多个候选标题，选择后只更新当前编辑内容并同步提纲一级标题。所有建议都必须由用户应用，且提供放弃和撤销入口；只有“确认提纲并标记为已就绪”才会正式更新文章标题，暂存版本只保留编辑内容。优化请求不默认触发联网检索，事实缺口通过“需要补研”提示交还资料调研工作台。

点击“新建文章”后，用户在同一表单中填写主题/想法，并可选填发布账号、写作目标、目标读者、核心角度、已有资料、指定资料链接、调研深度和标题；主题是唯一必填项。指定资料链接每行一条，系统自动抓取正文并生成资料卡，独立显示正在获取、已获取或获取失败状态；只有作者采纳资料卡后才进入写作依据，异常来源才需要人工处理。调研深度有快速核实、均衡调研和深入研究三档，只改变执行预算，不以资料卡数量定义结果。提交时统一创建文章与简报并直接进入联网补研，不再打开第二个“确认创作方向”窗口。已创建项目仍可通过“编辑创作方向”修改全部字段；该编辑窗口在末尾保留可编辑标题和“让阿文推荐标题”，让推荐拥有完整上下文，推荐结果在原位供选择，历史系列仅作为可见参考。

“第三步：补充资料”除资料卡筛选外，还应展示指定资料的自动获取状态；系统应直接抓取指定链接并尝试生成资料卡，只有登录、验证码、复杂网页交互、内容冲突或获取失败时才要求人工处理。搜索结果只能发现候选，自动资料卡必须展示正文核验摘录、提取时间和内容指纹，并说明主张、为什么值得看、质量/时效和证据边界；同质来源合并为一张卡，不设固定卡片数量。每张卡分开显示 AI 推荐与作者决定，作者可采纳、拒绝或标为待核验；当前作者决定必须通过状态按钮的选中样式清晰表达，其他按钮用于切换决定；在“资料卡纠错”中可将错误聚合的来源拆分，或将同一主张合并，且保留来源和决定。只有已采纳卡进入后续写作，资料中的链接和归因仅作为候选，正文不会自动插入。资料窗口顶部显示研究计划、证据维度、时效/冲突提醒、材料覆盖和仍有缺口；预算耗尽或维度未覆盖时明确标注“部分调研”，不得显示为充分完成。它提供“刷新易变事实”，只复核产品能力、价格、规则、版本、限额和适用条件，且保留当前背景资料和作者决定；同时展示当前资料之外的不可变运行历史，供回看每轮的计划、结论、快照和决定；失败、取消或暂停的运行也必须保留原始要求、错误和检查点，失败或取消记录可沿用原请求重试，不要求用户重新填写；不再需要处理的失败或取消记录可移除出历史列表，但必须保留资料卡、结论和审计事件。运行历史、时效刷新和资料卡纠错共用工具栏下的页面内辅助面板，一次只展开一个，不能用固定浮层遮挡资料卡；工作台打开时只保留工作台自身的纵向滚动，正文按窗口宽度收缩，不产生页面级横向滚动。它还应提供紧邻资料卡的“继续补研”输入区，可新增指定资料链接并选择本轮调研深度。用户可以自然语言补充要核查的事实、优先来源、时间范围、反例或排除项；点击后在原窗口保留已有结论和资料卡，以按钮的进行中状态展示阿文正在补研。联网失败时应区分网页验证、网络/TLS 连接和服务异常，只在需要网页验证时引导用户打开辅助浏览器；已有资料卡和历史运行必须保留。新结论追加到研究结论中，重复 URL 不新增资料卡；该轮用户要求和阿文回应会作为本文最早的阿文会话记录，供进入编辑器后回看。

新建文章时，如当前仅有一个已绑定账号，自动选中它作为发布账号；有多个账号时保留“暂不选择”，由用户明确选择，避免把内容误投到错误平台。

新建校验失败必须指出具体字段和原因（例如主题过长、标题为空或账号格式错误），不能只显示笼统的“提交信息不符合要求”。

“技能与模型 → 联网检索服务”中的 Tavily 连接测试必须在当前弹窗内立即给出可见结果：成功时展示已获得的测试结果数量，以及未保存 Key 还需保存的下一步；失败时展示服务返回的具体原因。不得仅结束加载状态而没有反馈。

首页默认结构：

1. 顶部显示当前工作空间、AI 连接状态、公众号连接状态。
2. 主操作为“新建文章”。
3. “继续创作”显示最近 3 个未完成项目，并给出业务化下一步。
4. “需要处理”只显示真实异常，例如朱雀需要接管、微信回调失败、IP 白名单变化、定时任务错过。
5. “最近发布”显示最近文章和基础数据。

不在首页直接展示账号添加表单、文章库路径输入框或长列表配置。

## 4. 归档库

归档库的已归档文章仍以 VitePress `docs/posts/<标题>/index.md` 为正文事实源。ContentFerry 创建的项目会在点击"新建文章"时立即生成该文件；扫描出的已有文章直接进入同一个编辑和发布流程。项目数据库只补充 AI 简报、提纲、检测和发布状态，不另存一份用户需要维护的正文。

每行显示标题、来源、账号、更新时间、状态和下一步操作。支持搜索和筛选。已有文章至少支持：

- 打开并编辑正文；
- 保留原 Front Matter，只编辑正文和明确开放的元数据字段；
- 查看网站发布字段 `publish` 与 `tags`；
- 发起公众号渠道稿生成；
- 查看历史发布记录；
- 外部文件变化时提示冲突，不静默覆盖。

账号、作者、摘要和封面统一在创作工作台右侧“发布设置”维护。点击“准备发布”只执行缺项检查和确认，不再出现第二套可编辑表单。

**发布设置按账号平台切换（2026-09-05 确认）：** “发布账号”决定发布去向，切换账号后配置项随之切换，平台专属参数不在这里维护第二份：

- 选**微信公众号**：显示微信留言、申请原创声明、开启赞赏、加入合集等微信专属选项，顶栏按钮为“准备发布”；
- 选 **CSDN / 博客园 / 掘金 / 51CTO**：面板内提示“在 XX 渠道稿中发布”，顶栏按钮变为“进入 XX 渠道稿”，点击后先保存文章设置再打开对应渠道稿；这些平台的栏目、分类、标签、发布形式等平台专属设置全部在渠道稿中填写，这里保存的作者、摘要和封面会带到渠道稿。

此前非微信平台选了账号后既没有对应配置项，顶栏“准备发布”又只会打开微信专用的同步草稿弹窗（提示“不是微信公众号”），形成死路。归档库“重新发布”入口正是走这条路径，因此必须按平台交接。

归档库的归档与查阅定位、与工作台的职责边界及发布入口归属见 §4.1。

## 4.1 工作台与归档库的职责边界（2026-08-26 确认）

两模块按"活跃工作集 vs 归档仓库"划分，明确"哪里操作、哪里查阅"，降低认知负荷。划分依据是 VitePress 源文件 Front Matter 中的 `archived` 布尔标记（随正文一起持久化，重新扫描不会丢失，无需数据库迁移）。

**工作台 = 未归档集合视图。** 基于 VitePress 目录扫描结果，不含 `archived: true` 的文章。范围包括：

- 本应用通过"新建文章"创建的草稿；
- 外部直接写入 VitePress 目录、经扫描纳入的文章；
- 任何尚未标记为归档的文章（含从未发布、部分渠道已发布、正在重发的文章）。

工作台提供完整操作：新建、修改、发布到各平台（微信公众号 / CSDN / 博客园 / 掘金）。

**归档库 = 已归档集合视图。** 只展示 `archived: true` 的文章，以查阅为主：检索历史文章、按渠道查看发布状态、阅读正文、查看发布记录；每行右侧提供 ⋯ 图标展开操作区，收拢"重新发布"与创作档案查阅入口，不实现第二套发布 UI。

工作台与归档库共用同一套渠道状态条：固定展示每个已接入平台的品牌图标和状态图标，尚未生成渠道稿时明确显示“未”，两处都显示有边框的创建/继续按钮；归档库的按钮只负责对应渠道稿交接，重新发布仍走独立入口。工作台每篇文章按“标题与右对齐时间 → 状态与发布账号 → 渠道状态条 → 文章操作”分层排版，渠道状态条独占一行并允许换行，避免长标题与平台按钮争抢横向空间；文章操作集中在底部工具栏，按钮采用统一紧凑尺寸，删除操作使用同规格危险按钮保持视觉区隔。首次进入应用时，四个平台的渠道稿与发布任务必须与文章库并行加载，状态条不得先以空数据渲染、再依赖切换页面才校正。两处列表的文章标题后均显示浅灰小字号的完整创作时间戳，并统一靠右对齐。发布记录的最终状态固定在列表右侧，不能因长标题换行或下移；完成记录的元信息不重复显示最终状态。导入文章的状态文案使用“文章正文可编辑，也可发布到其他平台”，不使用容易让用户误解来源性质的“外部文章”前缀。左侧一级导航支持收缩为图标栏，收缩后仍保留放大的图标、悬停提示和当前页高亮。

**归档判定（已落地）：**

- `archived` 标记为 true 的文章进入归档库；为 false（或字段缺失）的文章留在工作台；
- 自动归档：当某文章所有已接入账号的渠道（只看实际配置了账号的平台）均达到 `published` 终态时，自动将 `archived` 设为 true；
- 存量迁移：应用首次启动时自动把 2026-08-11 之前创建且尚未归档的文章一次性标记为 `archived`（用于把存量历史文章迁移进归档库），并通过 `appSettings.legacyArchiveMigrationDone` 保证只执行一次；
- 工作台列表按文章创建时间倒序排列（与归档库排序一致）；工作台为空但存在已归档文章时，提示去归档库查看。

**文章生命周期与发布入口归属（方案 A）：**

- 首次发布在 **工作台** 发起；
- 已归档文章如需换渠道或重发，从归档库 ⋯ 展开操作区的"重新发布"轻量入口跳回工作台，复用同一套发布流程；发布逻辑只维护在工作台；
- 状态机：未归档（工作台）→ 全平台发布 → 自动归档（归档库）；后续重发由归档库轻量出口回到工作台，两条路径闭环。

## 4.2 归档库操作区与创作档案查阅（2026-08-29 确认）

归档后文章的操作入口与创作过程资产查阅方式：

- **收拢为图标展开区**：每行右侧只保留一个 ⋯ 图标按钮，点击后在该行下方展开操作面板；展开态独占，展开一行会自动收起上一行。行内默认保持安静，也避免为没有创作记录的文章渲染无意义按钮。
- **操作按文章实际记录出现**："重新发布"恒有；"查看创作方向""查看素材""查看提纲"仅当该文章存在文渡内容项目（按 `source_relative_path` 反查）且对应资产已就绪时出现。外部直写文章没有内容项目，展开后只显示"重新发布"并给出说明。
- **按需懒加载**：创作档案在首次展开时才按文章相对路径反查项目及其就绪标志，不在列表渲染时逐行请求。
- **工作台同步**：生成提纲或正文后，"编辑创作方向"改为"查看创作方向"。此前该入口在成文后被隐藏，导致创作简报与用户原始资料笔记无法再回看。
- **只读语义**：从归档库打开的提纲沿用已发布文章的只读模式，不形成第二份可编辑正文。

**外部直写文章的纳入：**

- 文章可绕开工作台、直接手写进 VitePress 目录，其创建不发生在工作台；
- 工作台须提供“扫描 VitePress 目录 / 导入外部文章”动作（复用现有“重新扫描文章库”能力），将未索引的外部文章纳入并显示、可编辑、可发布，与工作台原生稿能力一致；
- 不强制用户先“认领”外部文章，发现即可编辑 / 发布；
- 无论来源，点文章均用同一编辑器直接改 VitePress 源文件，编辑能力无“原生 / 外部”差别。

## 5. 全屏创作工作台

### 5.1 页面布局

全屏工作台不使用模态弹框：

```text
┌ 返回归档库 | 标题 | 保存状态 | 预览 | 发布准备 ┐
├────────┬────────────────────┬───────────────┤
│文章导航 │   所见即所得正文编辑区 │ AI 助手/手机预览 │
│资料来源 │                     │ 文章设置/质量优化 │
│素材库   │                     │               │
└────────┴────────────────────┴───────────────┘
```

- 左栏可以折叠，显示文章大纲、资料和素材。
- 中间是唯一主滚动区，页面外壳不跟随长文章滚动。
- 右栏可在“AI 助手、手机预览、文章设置、质量优化”之间切换。
- 顶部保存栏固定，显示“正在保存 / 已保存 / 保存失败”。
- 当目标账号是微信公众号时，文章设置还包含“文章由 AI 生成”“申请原创声明”“开启赞赏”和“加入合集”。从工作台的微信公众号“设置并发布”进入编辑器时，若文章尚未保存发布账号，自动选中第一个已绑定的微信公众号账号；已有选择不覆盖。设置旁明确说明：勾选“文章由 AI 生成”只表示用户确认发布来源，创建草稿后会由可见浏览器尝试在微信编辑器中选择“内容由AI生成”；用户仍需在微信后台核对并点击最终发布。发布记录的主操作为“在微信后台完善并发布”，而不是让用户回忆草稿箱位置。

### 5.2 编辑能力

基础能力至少与公众号图文写作相匹配：

- 标题、作者、摘要、封面；
- 摘要生成属于独立的 AI 请求：等待模型返回期间不锁定正文编辑器、右侧栏滚动或文章保存，只锁定“AI 生成适配摘要”按钮防止重复请求；结果返回后写入当前草稿，仍需保存文章才持久化。
- 标题层级、粗体、斜体、删除线、引用、列表、分割线、链接；
- 图片选择、拖拽、粘贴、替换、裁剪、压缩、alt 文本和图注；
- 表格、代码块和一键清除格式；
- 撤销/重做、字数、图片数、预计阅读时长；
- 手机端实时预览；
- 公众号排版主题；
- Markdown/Word 导入和 Markdown 源码切换作为高级能力。

编辑器技术路线优先评估 `doocs/md` 的公众号主题与渲染能力，并比较 Tiptap 的图片上传、拖拽、可扩展节点和 React 集成。现有 Milkdown 只作为过渡实现，不再继续围绕其堆叠公众号专用能力。

### 5.3 图片生命周期

打开长文章时，所见即所得编辑器优先保证正文和首张图片可交互：SVG 转 PNG 必须使用可复用缓存和后台线程，图片接口支持 ETag 重验证；首屏外图片使用原生懒加载和异步解码，不得因为等待图片转换而锁住文章滚动。

1. 用户选择、拖拽或粘贴图片；
2. 图片先保存到当前文章的本地素材目录；
3. 自动生成预览图并提供压缩、裁剪；
4. Markdown 保存稳定的 ContentFerry 素材引用，不保存临时 `blob:` 地址；
5. 发布微信公众号前上传到目标账号素材库，并在冻结的渠道渲染包中替换为微信 URL；
6. 同一图片按文件哈希和目标账号复用远端素材。

联网找图的配置入口位于“技能与模型”而不是编辑器的独立全局资产库。图片初审模型提供三种选择：“关闭 AI 初审（仅规则筛选）”“跟随当前阿文模型”“指定模型连接”。页面必须显示当前连接是否支持图片输入；自定义连接未验证时显示“待验证”，ModelScope/Agnes 等不支持图片输入的连接不可选。文章编辑器左侧“图片素材”提供“打开联网找图”和“查看搜图历史”入口；历史按当前文章保存搜索词、时间、服务、候选和初审结果，保留最近 30 次。点击后在宽版弹窗中展示搜索框、缩略图、来源链接和“确认下载并插入文章末尾”按钮。点击候选图可以打开大图预览；若检索服务返回了源网页则提供源网页链接，否则只提供原图链接并明确说明源网页缺失。搜索结果只作为候选展示，用户确认前不得下载或修改正文。当前已接入 Codex 视觉初审：候选图会临时下载到 AI 沙箱，返回适配度建议后立即清理；初审失败或未启用时保留候选并标记为未初审，不能阻断人工选择。确认插入时统一追加到文章 Markdown 末尾，前后保留空行。

### 5.4 资料调研工作台与编辑器临时调研

- 调研进行中应同时显示已耗时与最近进度；超过 45 秒没有新进度时提示可能在等待来源响应，并保留暂停或停止入口，避免用户无法判断任务是在抓取还是卡住。

- 初始、继续和刷新调研均在独立全页资料调研工作台中管理；页面集中显示研究计划、覆盖缺口、资料卡、指定资料、运行控制和不可变历史，并提供返回创作方向与进入提纲的出口。提纲已生成后，同一出口区域还提供「按已选资料重新生成提纲」（先确认再按当前已采纳资料重生成，确认前不覆盖原提纲，生成后可在提纲编辑器恢复原提纲）与「修改标题」（随时改标题或让阿文推荐候选，保存后同步列表与目录）；进入提纲的按钮随状态显示「编辑提纲 / 继续编辑提纲草稿 / 用已选资料生成提纲」，且只打开既有内容、不会静默重生成。
- 正文编辑器左侧“资料来源”除正文链接外，还显示当前编辑会话的临时调研结果与已保存证据。临时调研支持选中文本、当前段落和整篇文章三种范围，并显示实际范围、抓取时间及易变主张复核提醒；摘录和改写建议只可替换作者明确选中的当前正文，不能追加或改写其他位置。
- 临时结果不会自动改写正文、添加链接/脚注/归因或进入正式资料；作者可明确替换选区为摘录/改写建议，或保存为待核验证据候选。离开编辑器或应用重启后未保存结果清除，保存正文不会延长其生命周期。

## 6. AI 辅助方式

AI 助手不是单独的“生成全文”按钮集合，而是与当前选择和文章状态相关：

- 未选文字：继续写、调整全文结构、生成标题/摘要、检查账号定位；
- 选择文字：改写、扩写、缩写、举例、降低套路感、调整语气；动作选择后提供“补充要求（可选）”输入框，用于说明语气、目标读者、保留项、避免项或具体目标，支持 `Ctrl+Enter` 直接生成建议。
- AIGC 特征检测未选中文字时默认检测当前正文全文，按钮明确显示“检测全文内容”；选择文字后仅检测选区，按钮改为“检测选中内容”。正文为空时禁用检测，避免把空请求发送到外部检测工具。
- 资料面板：搜索补充资料、生成资料卡、插入引用候选；
- 图片面板：生成配图建议、AI 生成图片、裁剪和封面建议；
- 记忆提示：阿文使用账号、系列、平台、文章或工具记忆时，在会话中以可展开的“本次使用的记忆”显示来源和作用域；正文底部提供当前文章的记忆管理入口，可查看待确认候选、启用或删除记忆，并对遗忘操作二次确认。账号/系列/工具作用域的编辑、导出和恢复仍由后续管理页提供。记忆只能提供上下文，不能绕过当前工具和文件权限。
- 所有 AI 结果先预览差异，再由用户应用，不直接覆盖正文。选区快捷操作是向阿文补充“选区、动作与可选要求”的快捷入口；其请求和结果必须保存到本文阿文会话，并在会话内提供接受/拒绝建议的操作，不能因重新选择正文而丢失。
- 阿文的可应用建议必须锚定到唯一的正文片段，并明确显示“替换原文”“追加到原文后”或“插入到原文前”。建议对象只能提供可直接写入正文的 content 内容，分析反馈和修改理由必须与 replacement 分离，不能把“建议补充”“这里需要说明”等元话语当作可应用正文。用户接受建议后先按 operation 应用到当前草稿：替换建议才替换原文，追加/前置建议以独立段落插入且保留原文；建议卡显示“已应用到当前草稿，尚未保存”，不立即写成最终已应用记录；文章保存成功后才显示“已应用并保存”。同一 original 锚点可以提供多个替换或追加备选方案，接受其中一个时，其他仍待处理的同锚点方案必须同时标记为已拒绝。用户接受后可以继续润色已插入或已替换的文字，保存时不能因为建议文本不再与原 replacement 完全一致而把已接受决定恢复为待处理；保存失败时保留可重试状态，放弃未保存修改时建议恢复为待处理。正文只显示待处理且仍可锚定的建议；阿文会话必须保留原建议、操作类型、建议文本与“已应用并保存”“已拒绝”或“无法定位”的最终记录，不能为清理正文浮窗而删除会话历史。离开存在未保存建议应用的文章时，必须提供保存并返回、放弃本次修改和继续编辑三个选择。
- 编辑模式切换使用紧凑图标按钮并提供悬停说明；视觉模式切换器靠工具栏右侧对齐，Markdown 模式沿用同一编辑器工具栏的背景、边框和层次，不能因模式切换出现突兀的配色变化。所见即所得模式的结构化工具栏默认在编辑交互停止约 1.8 秒后淡出，鼠标移入工具栏原来的顶部区域、点击、聚焦或键盘操作时重新显示；滚动正文不应唤回工具栏，正文区域内普通的鼠标移动也不应唤回工具栏；只读预览不显示工具栏。选中文字后的浮动工具栏和文章顶部工具栏都提供黄色背景高亮按钮，应用和取消使用同一套 Obsidian 风格的 `==文本==` Markdown 标记。文章底部的“管理本文记忆”“收起”和“发送”共用右侧输入区底部的紧凑操作行，不能再单独占用对话区顶部高度；左侧对话从面板顶部开始，记忆弹窗按已启用、待确认、备份恢复和删除记忆分区，删除操作与普通操作视觉隔离并需二次确认。
- 建议卡默认显示在对应段落之后并为其预留空间，不遮盖后续正文；用户可拖动卡片，拖动偏移相对该段落保存，切换所见即所得与 Markdown 原文后仍回到同一锚点。阿文对话中的待处理建议提供“定位”操作，点击后将正文编辑区滚动到对应原文片段并短暂高亮。
- 多条建议命中同一段落时，建议卡按生成顺序垂直堆叠并分别保留操作入口，不能相互遮盖而只显示最后一条。
- 阿文请求发出后，用户消息必须先显示“正在发送”；模型或网络失败时保留原消息并在消息旁说明失败，不能静默移除用户已经发送的内容。
- 在同一篇文章中继续提问前，若历史会话仍有未处理且能定位到正文的建议，输入区先显示待处理数量和确认操作：批量拒绝并继续、保留建议继续提问、取消发送。已应用到未保存草稿或已失效的建议不计入数量；批量拒绝未完成时不发送新问题。
- 失败消息提供就地“重新发送”操作；重试复用同一客户端消息 ID，避免因网络中断而在会话中重复保存同一条用户输入。
- 对旧版本留下的历史会话，若最后一条为用户消息且其后没有阿文回复，也应标为未完成并提供同样的重发入口。

### 6.1 代码与工具

“代码与工具”不是窄侧栏表单，而是从文章编辑器左侧打开的宽版执行面板。只有用户明确需要执行 Demo、读取源码或查看系统工具时才打开；普通编辑和联网补研不显示执行参数。目录授权可保存为所有文章共享或仅当前文章使用，面板会列出可复用的授权目录；但每次运行仍须确认具体目标、结构化参数、网络和目录读写，历史授权不能替代本次确认。当前版本阿文可以提出工具计划，实际执行仍由用户在面板中触发；后续接入模型工具调用时，授权请求应在模型确实提出执行计划后以同一面板按风险逐项询问。

点击“起草正文”且正文尚未生成时，先进入“最小实践计划”窗口。阿文根据提纲和已采纳资料提出不超过三项的必要实践；作者可直接编辑、暂存，展开同一窗口的“代码与工具”执行或记录已有实践，再确认计划并起草。若本机已具备软件、已有同类结果或作者决定不执行，选择“不新增实践，直接起草”会保留这一决定。计划与计划中的预期不展示为实验结果，正文只能引用已保存的实验观察。生成期间窗口显示当前阶段、已等待时间和正在写入的计划内容，并提供“停止生成”；停止后本次未保存的内容不会写入，作者可稍后重试。

### 6.2 编辑器内工具调用与证据结果（2026-09-21 已确认，第一阶段已实现）

授权交互只有一个实际入口：右侧“执行活动”展示工具、目标、参数和授权按钮；底部阿文对话区只显示等待状态并提供跳转，不重复渲染授权卡。用户可在“技能与模型”设置阿文专属工作区，工作区内的 Git staging 与分析不重复询问目录边界。

编辑器内的工具调用统一从“右侧执行活动”进入：文章正文保持主工作区，右侧显示可折叠的活动摘要；展开后显示当前执行目标（本机、WSL、Docker 或 Sandbox）、操作、参数范围、权限决策、耗时、结果和失败原因。对话时间线与研究抽屉作为同一能力的辅助视图，不改变执行语义；研究抽屉用于查看临时结果、实验观察和证据来源链。

“展开查看”以浮窗展示同一工作流的完整活动，便于阅读长时间线、参数、工具结果和回传内容；浮窗只是活动的放大视图，不新增授权入口。

阿文可以在新建草稿或编辑已有文章时提出工具调用。新建草稿中的低风险结果可以直接吸收进当前草稿，但仍保留工具结果和来源链；编辑已有文章时，结果只生成锚定到正文的建议，由用户决定应用。任何工具结果都不能自动成为已确认事实。

权限请求必须使用独立卡片展示操作、目标、风险和授权租约范围，并提供“仅本次”“本任务”“本项目”等选项。低风险、已授权且未扩大范围的连续读取可以自动执行；跨目录、跨网络、安装、删除、写入、外部副作用或目标边界变化时重新询问。用户拒绝某个操作只阻止该操作及等价绕过，阿文仍可提出替代方案，但替代方案必须重新经过策略判断。

结果操作分为三个独立动作：将结果应用为文章建议、保存为待核验实验观察、采纳为证据卡。三者不能合并为一次确认；“应用到文章”不等于“采纳证据”。当前右侧执行活动已显示工作流状态、事件时间线、权限卡、取消/恢复入口和 Git 摘要；Git 摘要已支持保存为待核验证据及单独采纳为证据卡，“应用为文章建议”仍为规划中动作，界面不得把保存或采纳伪装成正文修改。拒绝后的替代方案、取消、中断和不确定结果均须保留在执行活动和审计记录中。

## 7. 朱雀自动检测技能

主路径：

1. 用户点击“自动检测 AI 特征”；
2. ContentFerry 保存当前正文快照和哈希；
3. 打开持久化的可见浏览器会话；
4. 自动进入腾讯朱雀文本检测页；
5. 自动填入正文并触发检测；
6. 等待结果稳定，读取总体指标和可识别的疑似片段；
7. 保存结果、截图、检测时间和执行方式；
8. 返回编辑器右栏，按疑似片段提供定位和 AI 优化建议。

仅在以下情况进入人工接管：

- 尚未登录；
- 出现验证码或安全验证；
- 页面结构变化，无法可靠定位输入或结果；
- 内容长度超出网页限制；
- 结果读取不确定。

接管时保持浏览器可见，并在 ContentFerry 中显示“等待你完成登录/验证”。用户完成后点击“我已处理，继续自动检测”，技能从检查点恢复。人工回填放在折叠的“无法自动读取结果”兜底区，不作为默认操作。

## 8. 竞品启示与 ContentFerry 差异

新榜小豆芽与蚁小二的共同优势是左侧模块导航、多账号集中管理、内容发布和素材集中管理；公众号编辑工具的共同模式是中间编辑、图片/素材入口、手机预览及发布设置。

ContentFerry 不照搬它们的“批量分发工具”定位，而形成以下差异：

- 从主题、想法和资料开始的 AI 研究与创作；
- VitePress/Obsidian 文章库双向使用；
- 微信公众号官方 API 发布闭环；
- 朱雀自动检测与可恢复人工接管；
- CSDN 独立渠道稿与受控自动发布；
- 主稿、渠道稿、检测与发布回执的可恢复工作流。

## 9. 实施顺序

1. 应用外壳、工作台和一级导航；
2. 统一文章库视图（工作台 + 归档库），支持打开 VitePress 已有文章；
3. 全屏创作工作台和稳定保存；
4. 图片插入、本地素材和手机预览；
5. AI 选区助手；
6. 朱雀自动检测技能；
7. 微信渲染包、预览和发布设置；
8. 发布日历与数据回收。
